# 虚拟盘零块回收 + 写回缓存刷盘演练（Flask + raw 稀疏镜像）

虚拟磁盘里**写成零的块仍然占着宿主盘空间**：文件系统不会因为内容全零就自动释放它。
本项目提供一个网页，预置一张存于数据卷的 raw 镜像（内含稀疏空洞、写过的零块、非零块），
可以：

- 模拟虚拟机按 **4 KiB 块** 读写；写入先进**内存缓存**、读立即看到最新值；
- 点“**立即刷盘**”把一批缓存写入经 **WAL 恢复记录**原子地落进 raw 镜像，
  供测试人员用 `kill -9` / `docker kill` **演练掉电**；
- 一键发起/中断零块回收，实时查看镜像文件的**逻辑容量**与**宿主实占字节数**；
- 观察回收只给“已写入且全零的整块”打洞（`fallocate(PUNCH_HOLE)`），
  **不改变盘容量、不改变任何块的读值**。

## 刷盘（写回缓存 + WAL）语义

| 行为 | 实现 |
| --- | --- |
| 写入先进缓存 | 4 KiB 写只进内存字典，读块立即看到最新值；页面卡片与网格金边显示**待刷盘块数** |
| 刷盘快照语义 | 一轮刷盘只提交**开始时已在缓存**的内容；刷盘进行中的同块新写入立即可读，但带新序号留在缓存里**留到下一轮** |
| 忙 | 一轮未结束时再次发起刷盘，`POST /api/flush` 返回 **409**，页面提示“忙” |
| 读写不等刷盘 | 刷盘的磁盘 I/O（写恢复记录、`pwrite`、`fsync`）不持有缓存锁；块读写只经内存与既有块锁，等宿主盘写入期间照常完成 |
| 整批原子 | 每轮先写**恢复记录**（`disk.raw.journal`：magic + 本批全部块 + SHA-256 校验和）并 fsync，再逐块写回 raw 镜像并 fsync，最后删恢复记录；**返回成功时整批已写入原 raw 镜像** |
| 掉电恢复 | 重启时：恢复记录完整 → 重放整批（**全部留下**，重放幂等）；恢复记录缺失/残缺 → 整批丢弃（**全部丢弃**，镜像从未被本轮触碰）。从未纳入刷盘的写入随进程退出丢弃 |
| 每轮最小写入 | 每轮只写本批涉及的块与必要的恢复记录，不触碰其它块 |
| 回收与刷盘错开 | 零块回收继续直接作用于 raw 镜像（缓存不刷盘它看不见缓存）；触发回收时缓存仍留在内存，刷盘后新落盘的零块下一轮回收即可打洞 |

掉电演练钩子：环境变量 `FLUSH_DELAY_MS`（默认 0）。设为如 `500` 时，刷盘在
“恢复记录已提交”以及每块回写前各睡该毫秒数，把毫秒级的掉电窗口放大到秒级，
方便在刷盘中途 `kill -9` 观察整批原子性（重启后页面“本次启动恢复重放块数”
会显示重放了多少块）。

## 零块回收原理与关键保证

| 机制 | 实现 |
| --- | --- |
| 跳过已有空洞 | 扫描用 `SEEK_DATA`/`SEEK_HOLE` 定位已分配数据段，整段跳过空洞（含历史已打的洞） |
| 只回收整块零 | 段内只处理 4 KiB 对齐的整块；打洞前在块锁内重新校验“仍已分配且全零”，再 `fallocate(PUNCH_HOLE\|KEEP_SIZE)` |
| 容量/读值不变 | `KEEP_SIZE` 保持文件大小；打洞区域读回仍是零，非零块完全不触碰 |
| 读写不等扫描 | 块读写与回收在同一进程内通过**每块一把锁**互斥，锁只覆盖单个 4 KiB 操作，不做全局暂停 |
| 不抹新数据 | “判零 + 打洞”在块锁内原子完成；判零后到达的写入会让二次校验失败而跳过该块 |
| 中断可恢复 | 打洞定期 `fsync`；中断在块边界优雅停止。回收状态只存在于镜像文件本身，进程重启后镜像与已打的洞都保留，可随时重新发起，扫描自动跳过旧洞 |

> 说明：本项目用宿主文件系统的稀疏文件模拟虚拟磁盘，`st_blocks*512` 即宿主实占字节，
> 与真实虚拟化场景中虚拟盘文件占用宿主空间的语义一致。要求底层文件系统支持
> `fallocate` 打洞（ext4/xfs 及基于 ext4 的 overlay2、docker 命名卷均支持；
> 个别网络文件系统不支持，启动时会报错）。

## 目录结构

```

  web.py             Flask 路由与应用工厂

  cli.py             init-image / serve 命令
  static/            前端页面（块网格、实占/待刷盘卡片、刷盘与回收控制、块读写、事件日志）

  test_disk.py       纯 stdlib 自测（13 项，含并发写入与中断重跑）

```

## Docker Compose 启动（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

- 镜像文件固定在命名卷 `disk-data` 挂载的 `/data/disk.raw`，恢复记录为同目录的
  `disk.raw.journal`；容器重建不丢盘、不丢洞、不掉已提交的刷盘批；
- 环境变量 `BLOCK_COUNT`（默认 256，即 1 MiB 镜像）、`FLUSH_DELAY_MS`（默认 0）
  可在 `docker-compose.yml` 调整；
- 容器启动时先幂等初始化镜像（已存在且容量匹配则直接复用），再以
  gunicorn 单进程 8 线程运行（回收/刷盘在各自线程，块操作走块级锁）。

掉电演练示例：

```bash
# 1. 在 compose 里把 FLUSH_DELAY_MS 调大（如 500）后重启，或直接 docker exec
docker compose up -d --build
# 2. 网页上写若干块，点“立即刷盘”，在刷盘进行中：
docker kill $(docker compose ps -q disk-reclaim)
# 3. 重新启动，观察“本次启动恢复重放块数”和块数据：进行中的一批要么全在、要么全不在
docker compose start
```

停止与清理：

```bash
docker compose down            # 保留数据卷
docker compose down -v         # 连同镜像卷一起删除（下次启动重新预置）
```

## 本地直接运行（无 Docker 时）

```bash
# 有 Flask 时
pip install -r requirements.txt
IMAGE_PATH=./data/disk.raw gunicorn --workers 1 --threads 8 'app.web:create_app()'

# 没有 Flask 也可以跑（纯标准库回退入口，API 完全相同）
IMAGE_PATH=./data/disk.raw FLUSH_DELAY_MS=500 python -m app.server_stdlib
```

## 预置镜像布局（256 块 × 4 KiB = 1 MiB）

| 块区间 | 类型 | 是否占宿主空间 | 回收行为 |
| --- | --- | --- | --- |
| 0–63 | 稀疏空洞（`ftruncate`） | 否 | 扫描跳过 |
| 64–127 | 写过的全零块 | 是 | 打洞释放 |
| 128–191 | 非零块（含块号标记） | 是 | 判非零跳过 |
| 192–255 | 稀疏空洞 | 否 | 扫描跳过 |

初始实占 524288 B（128 块）；完整回收后实占 262144 B（仅剩 64 个非零块），容量始终 1048576 B。

## HTTP API

| 方法/路径 | 说明 |
| --- | --- |
| `GET /api/status` | 容量/实占、每块状态（缓存视角）、回收任务进度、刷盘状态（待刷盘块数、轮次、恢复重放块数等） |
| `GET /api/blocks/<i>` | 查看块状态、hex 全文与 ASCII 预览（缓存视角，立即看到未刷盘写入） |
| `POST /api/blocks/<i>/read` | 模拟虚拟机读（只读，不改任何状态） |
| `POST /api/blocks/<i>/write` | 写 4 KiB 进缓存，body：`{"hex": "..."}`（必须恰好 8192 个 hex 字符） |
| `POST /api/blocks/<i>/write-pattern/zero|data` | 便捷写全零 / 非零图案（进缓存） |
| `POST /api/flush` | 同步刷盘：返回成功时整批已写入 raw 镜像；一轮进行中返回 **409 忙**；缓存为空时为空操作 |
| `POST /api/reclaim/start` | 发起回收（已在运行则返回当前状态） |
| `POST /api/reclaim/cancel` | 请求中断，当前块处理完即停，已打的洞保留 |

## 自测

```bash
python3 -m unittest discover -s tests -v
```

共 32 项，全部通过（Python 3.11，本机无 Flask/Docker，走纯标准库入口）：

- `test_disk.py`（13 项）：预置布局与实占统计；完整回收（只打零块、容量/读值不变、
  二次回收空操作）；确定性的“判零后写入”竞争、4 线程高压并发写入零数据不丢；
  中断后重开镜像验证洞落盘、重启继续回收；API 输入校验与 WSGI 路由。
- `test_flush.py`（19 项）：写入进缓存读立即生效且 raw 镜像未变；刷盘落盘与恢复记录
  清理、空缓存空操作；**同块覆盖**（刷盘进行中新写入立即可读、留到下一轮，已用
  300ms 演练延迟确定性实测）；一轮未结束再刷盘 → `FlushBusyError` / API **409**；
  刷盘等宿主盘期间块读写照常完成；未刷盘写入随“进程退出”丢弃；已提交恢复记录
  重放（含手工构造的部分回写现场）、残缺/篡改记录整批丢弃；回收与缓存共存；
  **真实 `kill -9` 子进程演练**：恢复记录提交后杀 → 整批保留，回写中途杀 → 重放补齐，
  刷盘成功后杀 → 数据保留，未刷盘杀 → 整批丢弃。

另用真实服务进程（`app.server_stdlib`，`FLUSH_DELAY_MS=300`）做过一轮完整掉电演练：
写缓存 → 同块覆盖 → 409 忙 → 刷盘中 `kill -9` → 同数据目录重启 → 恢复重放 3 块、
整批保留；未刷盘写入在 `kill -9` 后确认丢弃。全部符合预期。

## 已知边界

- 刷盘原子性的前提是宿主文件系统 honors `fsync`（ext4/xfs 等均满足）；
  恢复记录与镜像在同一数据卷，两者一起丢失（如整卷损毁）不在本演练范围内。
- 打洞按 4 KiB 对齐；若数据段首尾不足 4 KiB 对齐（本项目镜像与写入都按 4 KiB 对齐，不会出现），零碎部分保留不动。
- 回收/刷盘任务状态保存在进程内存（进度计数），持久状态只依赖镜像文件与恢复记录；
  进程重启后进度计数归零，但已回收空间与已刷盘数据真实保留。
- 当前环境未安装 Docker，compose 配置未经本机实际启动验证；核心逻辑、HTTP 行为与
  掉电恢复均已通过纯标准库入口完整自测（含真实 `kill -9` 演练）。
